# Концептуальная схема данных «Заявки УК»

```mermaid
erDiagram
  ДОМ ||--o{ ЖИТЕЛЬ : "содержит"
  ДОМ ||--o{ ЗАЯВКА : "относится к"
  ЖИТЕЛЬ ||--o{ ЗАЯВКА : "подаёт"
  ЖИТЕЛЬ ||--o{ ЗАЯВКА_НА_ДОМ : "подаёт"
  КАТЕГОРИЯ ||--o{ ЗАЯВКА : "классифицирует"
  РАБОЧИЙ ||--o{ ЗАЯВКА : "назначен на"
  ЗАЯВКА ||--o| ОТВЕТ : "имеет"

  ДОМ {
    int id PK
    string адрес
  }
  ЖИТЕЛЬ {
    int id PK
    string фио
    string телефон
    int дом_id FK
    string квартира
  }
  КАТЕГОРИЯ {
    int id PK
    string название
  }
  РАБОЧИЙ {
    int id PK
    string фио
    string специализация
  }
  ЗАЯВКА {
    int id PK
    int житель_id FK
    int дом_id FK
    int категория_id FK
    int рабочий_id FK
    string статус
    string название
    string описание
    date срок_ответа
    date дата_создания
  }
  ОТВЕТ {
    int id PK
    int заявка_id FK
    string текст
    date дата
  }
  ЗАЯВКА_НА_ДОМ {
    int id PK
    int житель_id FK
    string адрес
    string статус
  }
```

- Один дом — много жителей и много заявок (1:N).
- Один житель — много заявок и много заявок на добавление дома (1:N).
- Одна категория — много заявок; один рабочий — много назначенных заявок (справочные связи).
- Заявка имеет не более одного ответа (1:0..1) — ответ появляется после исполнения.
Связь между ответом на заявку и рабочим решил не делать, т.к. по заявке и так ясно, кто прикреплен к ней, и кто ответит.
