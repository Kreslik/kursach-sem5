# Описание предметной области и требований к системе «Заявки УК»

## Предметная область

Система автоматизирует работу управляющей компании (УК) с обращениями жителей многоквартирных домов по бытовым проблемам.

Без автоматизации процесс обычно строится на звонке диспетчеру и бумажном или устном учёте заявок, из-за чего сложно контролировать сроки исполнения, загрузку рабочих и историю обращений. Именно эти узкие места закрывает система «Заявки УК».

## Участники и их роли

- **Житель** - подаёт заявку (дом, категория/вид проблемы, описание, при необходимости фото), следит за статусом, подтверждает выполнение или открывает заявку повторно при несогласии с результатом.
- **Рабочий** - видит только назначенные ему заявки (дом, категория, срок ответа), меняет статус (принята в работу -> выполняется -> выполнена), оставляет ответ по результатам исполнения.
- **Администратор (диспетчер)** - ведёт справочники домов, пользователей, категорий проблем и рабочих; назначает ответственного рабочего и срок ответа на заявку; контролирует сроки исполнения и выявляет просрочки; формирует отчётность.

## Ключевые сущности

Пользователь, Житель, Дом, Категория/вид проблемы, Заявка, Рабочий, Ответ на заявку.  

## Основные бизнес-процессы

1. **Обработка заявки жителя** - подача -> назначение рабочего и срока -> изменение статуса рабочим -> ответ рабочего -> подтверждение жителем либо автоматическое закрытие по истечении срока подтверждения, либо повторное обращение при несогласии с результатом.  
2. **Назначение и контроль исполнения** - распределение заявок администратором с учётом специализации и загрузки рабочих, автоматическое выявление просроченных заявок и уведомление участников.  
3. **Обработка заявок-дубликатов** — при возникновении однотипной проблемы (например, протечка на нескольких этажах) администратор может пометить новые поступающие заявки как дубликаты, привязав их к первой (основной) заявке.  

## Правила предметной области  

### Завершение заявки, несогласие жителя и дубликаты  

После того как рабочий отметил заявку выполненной и оставил ответ, заявка ожидает реакции жителя в течение срока подтверждения (например, 3 суток). Возможны три исхода:  

1. **Житель подтверждает выполнение** — заявка закрывается.
2. **Житель не реагирует** до истечения срока подтверждения — заявка закрывается автоматически с отдельным статусом («закрыта автоматически»).
3. **Житель не согласен с результатом** — нажимает «Не согласен с результатом» и указывает комментарий. Система создаёт новую заявку, копируя данные и устанавливая ссылку на исходную заявку (`исходная_заявка_id`). Повторная заявка поступает администратору для оценки обоснованности претензии.

Оценку обоснованности повторных обращений, а также связывание дубликатов производит только администратор.

### Пользователи и аутентификация

Все участники системы аутентифицируются по логину и паролю. Учётные записи (пользователей) создаёт администратор:
- При подключении дома администратор заносит данные жителей (ФИО, квартира, телефон) и создаёт их учётные записи.
- Учётные записи рабочих и администраторов также создаются администратором.

### Контроль сроков и просрочки

Для обеспечения контроля за исполнением заявок фиксируются точные дата и время следующих событий:
- Время создания заявки жителем.
- Время назначения рабочего. На назначение рабочего администратору отводится нормативный срок (не более 3 дней с момента создания заявки).
- Время фактического завершения работ рабочим.  

Срок ответа на заявку устанавливается администратором при назначении рабочего. Заявка считается просроченной, если срок ответа истёк, а заявка ещё не переведена в статус «выполнена».

Система:
- автоматически выявляет просроченные заявки и помечает их;
- выводит администратору список просроченных заявок с указанием рабочего и длительности просрочки;
- уведомляет рабочего о приближении срока ответа и о наступлении просрочки;
- фиксирует факт просрочки (заявка, рабочий, длительность) для формирования отчётности.

Меры воздействия на рабочих при просрочках (в том числе штрафные санкции, принятые в УК) применяются вне системы. Задача системы - вовремя дать администратору данные, на основании которых такие решения принимаются.

## Требования к системе  

**Архитектура**
- Монолитное веб-приложение: серверная логика (жители, дома, заявки, категории, рабочие, ответы, авторизация) и веб-интерфейс - единый процесс.
- Внутри монолита - модульное деление кода на независимые пакеты.
- Стек: Java + Spring, PostgreSQL, MinIO (файлы - фото к заявкам, вложения).

**Надёжность**
- Целостность данных о заявках, статусах и связях со справочниками при сбоях отдельных компонентов.
- Фиксация времени каждого изменения статуса заявки - для восстановления истории обработки.

**Безопасность**
- Доступ только после аутентификации.
- Разграничение прав: житель - свои заявки и заявки по своему дому; рабочий - назначенные ему заявки; администратор - все данные системы.

**Эргономика и интерфейс**
- Отдельный набор экранов для каждой из трёх ролей.
- Наглядное отображение статуса заявки и истории её обработки.
- Минимальное число действий на ключевые операции (подача заявки, назначение рабочего, изменение статуса, оставление ответа).

**Прочее**
- Отчётность администратора: по категориям проблем, срокам исполнения, загрузке рабочих, по домам.
- Уведомления: о назначении рабочего, смене статуса, поступлении ответа, приближении срока ответа.
